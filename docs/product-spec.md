## Purpose
アプリの目的・対象・非対象は [`AGENT.md`](../AGENT.md) の Purpose 節を正とする（本ファイルでは重複定義しない）。

## Domain terminology
信用買い・信用売りを扱うため、内部モデルで `BUY` / `SELL` だけに意味を詰め込まない。

- `PositionSide`: `Long` / `Short`
- `SignalPurpose`: `Entry` / `Exit`
- `ExitDecision`: `Hold` / `TakeProfit` / `StopLoss` / `Exit`

例:
- Long + Entry = 買いエントリー候補
- Short + Entry = 売りエントリー候補
- Long + Exit = 売却/返済候補
- Short + Exit = 買い戻し/返済候補

信用売りでは決済が買い戻しになるため、保有画面を一律「SELL 判定」にしない。
UI で BUY/SELL を表示する場合も、新規/決済と Long/Short の意味を明示する。

## Daily update workflow
主な運用は取引日の 15:30 以降に「更新」を実行すること。

1. 当日までの日足株価、企業アクション、取得可能な信用規制・制度逆日歩情報を更新
2. 日足確定状態、履歴完全性、企業アクションの利用可能時点を確認
3. 保有ポジションへ分割等の現在基準換算を適用し、企業アクション・期限・コストの要照合状態を更新
4. point-in-time 調整済み OHLCV を生成
5. テクニカル分析
6. Long 新規候補抽出
7. Short 新規候補抽出
8. 保有ポジション再評価
9. 入力manifest、パラメータスナップショット、結果を保存
10. UI 表示
11. 対象がある場合は AI チェックを永続キューへ投入し、結果を非同期反映

日次更新のコア完了は9で成立し、AI チェックの完了を待たない。初期対象は当日の Long/Short Entry 候補とし、保有ポジションのAIチェックは対象外とする。既定では利用者が単件または複数候補を選択して実行する。設定で自動チェックを有効化した場合だけ、各方向のスコア上位3件（スコア降順、同点は銘柄コード昇順）を自動投入する。AIが全件失敗しても候補抽出・保有再評価を無効にしない。

更新処理:
- 1銘柄の失敗で全体を即停止させない。
- 失敗銘柄と原因を記録する。
- 同一データを重複登録しない。
- 可能な限り冪等にする。
- UI に進捗、成功/失敗件数を出せる構造にする。

対象市場の範囲（スキャン対象銘柄・銘柄マスタ/信用情報の取得元）は [`data-sources.md`](./data-sources.md) を参照。

## Candidate list
最低限表示:
- 銘柄コード/銘柄名
- Long/Short
- Entry（初期リリース。Exit/Hold/StopLoss/TakeProfit は保有ポジション単位で Positions に表示）
- 判定日
- 適用戦略
- スコアまたは信頼度
- 主な判定理由
- AI チェック状態

スキャン対象外となった銘柄については、`InsufficientHistory`、`HistoryIncomplete`、データ不正等の理由と保有/必要履歴本数を確認可能にする。必須指標不足を単なる条件不一致として表示しない。

スコアを勝率・利益保証として表現しない。

AI状態は未実行、待機中、実行中、成功、失敗、timeout、情報不足、キャンセル、旧結果を区別する。単件/複数選択、待機中キャンセル、明示的な再試行を可能にし、実行中または同一入力の重複投入を防ぐ。再試行・再チェックは過去結果を上書きせず、新しい試行として保存する。
候補スコアの算出方法・重み付けの詳細は [`technical-analysis.md`](./technical-analysis.md) を参照。

## Positions
候補と保有ポジションは別概念として管理する。
ポジションと約定を分離し、1ポジションが複数の新規建・部分決済約定を持てる構造とする。最低限: 銘柄、Long/Short、元約定日時・価格・株数、現在基準の取得単価・株数、適用戦略、状態、メモ、決済情報、企業アクション調整履歴。

返済期限と契約条件は各新規建約定に対応する `MarginLot` 単位で保持する。同じポジションでも建玉日が違えば期限が異なるためである。各lotに制度/一般、証券会社・商品、`FixedDate / NoFixedTerm / Unknown`、証券会社で確認した最終返済可能日時、確認日時・根拠、契約条件revisionを記録する。制度信用でも単純な「約定日+6か月」を確定期限として自動採用せず、期限不明は要照合とする。制度/一般の区分を保有途中で書き換えない。

保有コストはlotに紐づく追記型台帳とし、買方金利、貸株料、逆日歩、配当金相当額、証券会社固有コスト、その他を Charge/Credit として保持する。見積と証券会社明細による確定額を分離し、訂正は旧記録を上書きせず supersede する。

保有画面で特に確認しやすくする:
- 適用戦略
- 現在の決済判定
- 判定日/判定理由
- 損切候補
- 利確候補
- HOLD 理由
- 固定ATR、ATR基準日、損切倍率、建玉時の戦略/リスクパラメータスナップショット
- 企業アクションの適用根拠、現在基準への換算内容、要照合状態
- 未決済lotの最短期限、残営業日、期限未確認/変更警告
- 保有コストの確定累計と未確定見積、価格損益、ネット参考損益、コスト/R比（欠損を0円扱いしない）

損切/利確ラインの具体的な算出ロジック(ATR倍数・R倍率・テクニカル反転条件)は [`risk-management.md`](./risk-management.md) を参照。
本アプリは自動決済・自動発注を行わない。上記はあくまで判断支援表示であり、実際の決済は利用者が証券会社側で行う。

## Trade records
約定履歴は必ず利用者の明示操作で登録する。
約定日時・約定価格・株数は手入力または利用者が明示選択し、保存前に確認可能にする。
候補一覧から銘柄や Long/Short を初期値として渡すのは可。
現在値、終値、サイン日時、AI 判定から約定情報を自動確定してはならない。
企業アクションによる現在基準換算は約定履歴と別の調整履歴に保存し、売買履歴を自動生成しない。元約定は監査原票として保持する。
部分決済をどのlotへ充当したかは利用者が確認して登録する。利用者確認なしに FIFO 等で推測しない。期限警告、コスト計上、AI結果から決済・約定履歴を生成しない。

## UI/UX
MahApps.Metro と既存スタイルへ合わせる。
派手さより可読性・誤操作防止・状態の明確さを優先する。

特に:
- 候補探索と保有管理を分離
- Long/Short、Entry/Exit を見間違えにくくする
- 判定日、適用戦略、判定理由を確認しやすくする
- 更新進捗を表示
- AI チェック中/成功/失敗を明示
- 日次更新の進捗とAIキューの進捗を分離し、「分析更新完了・AIチェック継続中」を表現可能にする
- AI Verdict は候補方向と切り離して表示せず、Long + Bullish / Short + Bearish は「候補方向と整合」、逆の組合せは「候補方向と逆」、Neutral は「中立」と併記する
- 履歴不足、企業アクション適用、要照合、point-in-time 非保証を明示
- 期限接近・期限未確認、逆日歩未公表/取得失敗、見積/確定コストを明示
- 判断支援情報であることを誤認させない
